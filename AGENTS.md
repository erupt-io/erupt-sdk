# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex, ...) when working with code in this repository.

## What this repository is

Node SDKs for erupt-cloud: a service written in any language declares models and owns their data (a *node*);
the erupt server renders the admin UI, logs users in and checks menus, and forwards each request to the node.
The framework and the server live in the erupt repository (`github.com/erupts/erupt`, usually checked out next
to this one as `../erupt`); the wire contract is `erupt-cloud/PROTOCOL.md` there.

One directory per language, each a self-contained package with its own README (user documentation plus a
"Generated code" / "Development" / "Tests" section):

| Dir | Package | Runtime dependencies |
|-----|---------|----------------------|
| `python/` | `erupt-sdk` (PyPI), Python 3.9+ | none |
| `go/` | `github.com/erupt-io/erupt-sdk/go`, Go 1.21+ | standard library (`modernc.org/sqlite` is test-only) |
| `ts/` | `erupt-sdk` (npm), Node.js 22+, ESM | none |
| `php/` | `erupt-io/erupt-sdk` (Packagist), PHP 8.1+ | none (`ext-json`, `ext-pdo`) |
| `dotnet/` | `Erupt.Sdk` (NuGet), .NET 8+ | none |
| `rust/` | `erupt-sdk` (crates.io, lib name `erupt`), Rust 1.85+ | serde, serde_json, ctrlc; drivers behind the features `sqlite`, `postgres`, `mysql` |
| `ruby/` | `erupt-sdk` (RubyGems), Ruby 3.1+ | none (Rack compatible) |
| `swift/` | `EruptSDK` (SwiftPM), Swift 5.9+ | Foundation; SQLite through the optional `EruptSQLite` product |
| `jvm/` | no SDK: examples only | `xyz.erupt:erupt-cloud-node-lite` / `erupt-cloud-node-jpa`, released with erupt |

Shared across languages: `schema/` (the contract generated by erupt), `conformance/` (the protocol suite and
its fixture spec), `SHOWCASE.md` (the spec of every `examples/showcase`), `scripts/release.sh` and
`.github/workflows/`.

## Architecture

- **Every SDK has the same parts**, under language-idiomatic names: model declaration (annotations /
  attributes / builders → the build JSON), the node runtime (registration and heartbeat, routing of
  `/erupt-api/...` and `/node-health`, signature check), repositories (a `Repository` interface, a memory
  one, SQL ones), the `Erupt-Signature` verifier, value conversion, and a **generated** types file.
  A behavior change in one SDK normally has to be made in all eight; the Python SDK is the one the other
  READMEs compare themselves to ("Differences from Python").
- **Protocol v2 only** (`PROTOCOL.md` §12, thin nodes). The node declares only what a model sets; the server
  completes and checks the build, enforces the user's rights and the model's, normalizes queries and
  records, and turns drills and link trees into plain conditions. The node stores rows and runs its own
  code. It must refuse an unsigned call or one missing a required `Erupt-Enforced` value, and it keeps
  checking field names, body shapes, its own keys and its page size whoever calls. Against a server that
  does not answer `protocolVersion: 2` it logs that the server needs an upgrade and stops registering; it
  never falls back to v1. The Java nodes speak v1 and live in the erupt repository.
- **`schema/` is the whole contract between the two repositories**: `erupt-annotations.schema.json` (JSON
  Schema of every annotation) and `erupt-node-defaults.json` (the resolved field templates, read only by the
  conformance suite). erupt regenerates them with `mvn -pl erupt-test -Pnode-schema test`. Never edit them by
  hand; the `sync-schema` workflow (weekly, or by hand with a branch / tag of `erupts/erupt`) downloads them,
  regenerates every language and opens a pull request. Locally, `python tools/gen_types.py <erupt
  checkout>/schema` copies the two files into `schema/`; the other generators read `../schema`.
- **Generated files — regenerate, never edit**: `python/src/erupt/_types.py`, `go/types.go`,
  `ts/src/types.ts`, `php/src/Types/`, `dotnet/src/Erupt.Sdk/Types.g.cs`, `rust/src/types.rs`,
  `ruby/lib/erupt/types.rb` + `ruby/sig/erupt/types.rbs`, `swift/Sources/EruptSDK/Types.swift`. No SDK embeds
  the schema at run time. Each language's CI fails when a generated file no longer matches `schema/`.
- **Shared repository rules** every SDK unit-tests: without a sort, rows come back by primary key ascending;
  SQL repositories bind every value, quote whitelisted identifiers and escape LIKE with `ESCAPE '!'`.
- **Signature**: `conformance/signature-vectors.json` holds vectors computed by the Java reference
  (`xyz.erupt.cloud.common.http.CloudSignature`); every SDK's unit tests check its verifier against them.
- **Examples**: each SDK has `examples/conformance` (the fixture of `conformance/README.md`, in memory) and
  `examples/showcase` (the application of `SHOWCASE.md`, on SQLite). A change to either spec means changing
  every language's example and the matching Python checker (`conformance/run.py`, `conformance/showcase.py`).
  Examples read `ERUPT_ACCESS_TOKEN`, `ERUPT_SERVER`, `PORT` (showcase also `ERUPT_NODE_NAME`, `ERUPT_DB`).
- **PHP runs as two processes** (`php -S` or php-fpm starts a fresh process per request): a front controller
  plus one long-running heartbeat process that registers; `MemoryRepository` therefore only suits tests.
- **`jvm/`** holds no SDK. `examples/conformance` and `examples/blog` (Kotlin) build against
  `erupt-cloud-node-lite`, `examples/spring-blog` against `erupt-cloud-node-jpa`; the version is
  `erupt.version` in `jvm/examples/pom.xml` and `jvm/examples/spring-blog/pom.xml`. The Java node's
  conformance and database tests run from the erupt repository.

## Commands

Run from the language directory unless noted. Each block is what that language's workflow runs.

```bash
# python/
python tools/gen_types.py ../schema --check          # generated file matches schema/ (drop --check to regenerate)
PYTHONPATH=src python -W error::DeprecationWarning -m unittest discover -s tests -v
PYTHONPATH=src python -m unittest tests.test_node -v # one test module

# go/
go run ./cmd/gentypes -check ../schema               # note: -check comes before the path
go vet ./... && test -z "$(gofmt -l .)"
go test ./...
go test -run TestName .                              # one test

# ts/
npm ci
npm run gen:check                                    # npm run gen to regenerate
npm test                                             # tsc build + node --test on dist/test/*.test.js
node --test dist/test/node.test.js                   # one test file, after npm run build

# php/
php tools/gen-types.php ../schema --check
composer validate --strict
php tests/run.php                                    # one self-contained runner, no test selection

# dotnet/                                            (warnings are errors: Directory.Build.props)
dotnet run --project tools/GenTypes -- ../schema --check
dotnet build -c Release
dotnet test -c Release --no-build
dotnet test -c Release --filter "FullyQualifiedName~NodeTests"

# rust/
cargo run --bin gen-types -- ../schema --check
cargo fmt --check && cargo clippy --all-features --all-targets -- -D warnings
cargo test --all-features
cargo test --all-features --test node                # one test file of tests/

# ruby/
ruby tools/gen_types.rb ../schema --check
ruby -w -Ilib -e 'Dir["./test/test_*.rb"].sort.each { |f| require f }'
ruby -Ilib test/test_node.rb                         # one test file

# swift/
swift run erupt-gen-types ../schema --check
swift build
swift test                                           # needs a Swift 6 toolchain (swift-testing); 5.9 only builds

# jvm (from the repository root)
mvn -f jvm/examples/pom.xml package                  # needs erupt-cloud-node-lite at erupt.version
mvn -f jvm/examples/spring-blog/pom.xml package
```

SQLite-backed Ruby tests run only where the `sqlite3` gem is installed. With only the Command Line Tools on
macOS, `swift test` needs the extra flags listed in `swift/README.md`.

### Conformance and showcase

`conformance/run.py` plays the erupt server (registration with a `/node-health` probe, signed v2 calls,
deregistration on SIGINT) against the command given after `--`; `conformance/showcase.py` does the same for
every scenario of `SHOWCASE.md`. Both are standard-library Python and run from the repository root; build
the fixture first where the language compiles. `CONFORMANCE_TRACE=1` prints stack traces.

```bash
python conformance/run.py -- python3 python/examples/conformance.py        # PYTHONPATH=python/src
(cd go && go build -o /tmp/erupt-go-conformance ./examples/conformance) && python conformance/run.py -- /tmp/erupt-go-conformance
(cd ts && npm run build) && python conformance/run.py -- node ts/dist/examples/conformance.js
python conformance/run.py -- php php/examples/conformance.php
(cd dotnet && dotnet build -c Release) && python conformance/run.py -- dotnet dotnet/examples/Conformance/bin/Release/net8.0/Conformance.dll
(cd rust && cargo build --release --example conformance) && python conformance/run.py -- rust/target/release/examples/conformance
python conformance/run.py -- ruby ruby/examples/conformance.rb
(cd swift && swift build -c release --product Conformance) && python conformance/run.py -- swift/.build/release/Conformance
python conformance/showcase.py -- <command that starts that language's examples/showcase>
```

A node that registers without `protocolVersion: 2` (the Java node) is checked against protocol v1 instead.

### Real databases

Every SQL repository is also tested against PostgreSQL and MySQL (the `databases` workflow, with throwaway
containers). Those tests are skipped unless `ERUPT_TEST_DATABASES` is set; connection settings come from the
standard `PG*` variables and `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_DATABASE`. Entry points:
`python -m unittest tests.test_databases`, `go test ./...` in `go/dbtest` (its own module with the drivers),
`node --test dist/test/databases.test.js`, `php tests/databases.php`,
`dotnet test --filter "FullyQualifiedName~DatabaseTests"`,
`cargo test --features postgres,mysql --test databases`, `ruby -Ilib test/test_databases.rb`.

## CI

One workflow per language (`.github/workflows/<lang>.yml`), triggered by changes under that directory,
`schema/` or `conformance/`: generation check, lint, unit tests, conformance. Minimum versions are part of
the matrix (Python 3.9, Go 1.21, Node 22, PHP 8.1, Ruby 3.1, Swift 5.9, Rust's `rust-version` in the `msrv`
job), so do not use newer language or standard-library features. A pull request opened with the workflow
token (`sync-schema`) does not trigger other workflows: close and reopen it, or push to its branch.

## Releasing

Each language is versioned and released on its own from `main`; details and one-time registry setup are in
`RELEASING.md`, the guided procedure in `.claude/commands/release.md`.

- A tag `<lang>/v<version>` (`python`, `ts`, `go`, `php`, `dotnet`, `rust`, `ruby`, `swift`) starts
  `release.yml`: that language's full CI, a check that the tag equals the version in the package metadata
  **and** the version the node reports to the server, the publish, then a GitHub release.
- The version therefore lives in two places for most languages (e.g. `python/pyproject.toml` and
  `__version__` in `python/src/erupt/node.py`); the table in `RELEASING.md` lists them. Change them only
  through `scripts/release.sh`.
- `scripts/release.sh <version> [lang...]` bumps, commits on `main`, and pushes one tag at a time;
  `--dry-run` shows the diff and changes nothing, `status` compares the repository with each registry,
  `bootstrap ts|rust` is the one manual first publish npm and crates.io require.
- Publishing uses OpenID Connect trusted publishing; no registry token is stored in the repository or on
  the machine. PHP and Swift are pushed to read-only split repositories (`erupt-io/erupt-sdk-php`,
  `erupt-io/erupt-sdk-swift`), since Packagist and SwiftPM read a repository root.
- A published version can never be reused: after a failed publish step check the registry before
  re-tagging. RubyGems writes a pre-release as `x.y.z.rc1`; Go stays on v0/v1 (v2+ needs a `/v2` module path).
- JVM nodes are released with erupt; after an erupt release only `erupt.version` in the example poms is bumped.
